# Linux/glibc experiment record

Initial execution: November 7, 2026. Continuation and packed-fixture experiment: November 8, 2026 (Europe/Istanbul). This record supplements the earlier assembly/GDB CI evidence; it does not replace it.

## Environment and reproduction

Docker Desktop's ordinary, isolated Debian bookworm container ran Linux `6.12.76-linuxkit`, **aarch64**, glibc `2.36-9+deb12u14`, GCC `12.2.0-14+deb12u1`, GNU binutils `2.40`, GDB `13.1-3`, and strace `6.1`. These are real Linux executions on an ARM virtual machine, not macOS syntax checks or Intel-hardware measurements. Container capabilities, seccomp, sysctls, host security policy, and tracefs mounts were not relaxed.

`python3 scripts/verify-linux-labs.py --output /path/to/evidence` extracts the published C blocks from Markdown. Additional, explicitly separate fixtures supply callers or negative controls where a guide publishes only a fragment. Requirements are GCC/libc headers, binutils, GDB, strace, and Python 3 on Linux/glibc. Optional probes use bpftrace, perf, and CRIU. Output includes source hashes, commands, exits, logs, generated sources, and `report.json`. Use a fresh output directory to keep earlier evidence.

## Observed results

All seven groups below passed on November 7 and were rerun successfully with the current sources and harness on November 8.

- **Memory permissions:** the published program's address was `rw-p`, then `r-xp`; strace recorded successful `mprotect` for that address. An unaligned-address control returned `EINVAL`. The source never transfers control into the mapping. A first RW VMA covered multiple pages and split after permission change: match the containing range, not an assumed one-page VMA.
- **Interposition and loader diagnostics:** ordinary execution returned 11 and preload returned 22. `LD_DEBUG=symbols,bindings` recorded both lookup and the main program's binding to `libb.so`. Rebuilding `liba` with `-Bsymbolic` kept the main call at 22; an additional internal-call fixture changed from 22 to 11.
- **Separate debug information:** GNU objcopy/strip/readelf and GDB source-line lookup passed. Appending bytes to the separate debug file caused a debuglink CRC rejection. A separate `.build-id/xx/rest.debug` lookup succeeded; substituting a different embedded Build-ID was rejected. Network debuginfod was disabled for these tests.
- **Linker map:** an extra two-file fixture placed its unused function in discarded input sections under `--gc-sections`; `nm` omitted it. Without GC the symbol remained. The published `etext`/`edata`/`end` C block also ran.
- **TRACEME/procfs:** the published reader exited 0 normally and 1 under GDB. A forked child observed its parent as tracer after successful TRACEME, while a second TRACEME returned `EPERM`. The parent handled the stop and continued the child; no existing process was attached.
- **memfd/fexecve/execveat:** the published function, called by a separate file-reading harness, executed an ELF payload through `execveat(..., AT_EMPTY_PATH)`. The PID remained the same, argv/environment reached the payload, and the CLOEXEC memfd disappeared from its fd list. A CLOEXEC script failed with `ENOENT`, an empty image with `ENOEXEC`, and a zero write with `EIO`; injected EINTR followed by a seven-byte short write recovered successfully. No fallback/procfs path or restrictive execmem policy was claimed tested.
- **Core:** both an actual kernel crash core and a GDB-generated snapshot were created. GDB loaded snapshot backtrace/registers/mappings. Included anonymous memory was readable; a `MADV_DONTDUMP` marker was inaccessible. This demonstrates bounded coverage, not a full-process reconstruction or restore. AArch64 registers were used; the guide's inspection now uses GDB's portable `$pc` alias. On November 8, a separate invocation of the published `gcore -o snapshot PID` command captured the running permission-lab process; the target remained alive after detach, exited normally, and the snapshot was read back with its source frame.

## Known packed fixture and OEP

`python3 scripts/verify-packed-oep.py --upx /absolute/path/to/upx --output /empty/evidence/directory` builds a small static ET_EXEC fixture, records original ELF entry bytes, packs/runs it, and observes a hardware breakpoint in a **live** GDB inferior. The first attempt queried hardware breakpoint support before creating the inferior and failed; `starti` before `hbreak` resolved that harness ordering error without changing host policy.

The November 8 run used [UPX 5.3.0](https://github.com/upx/upx/releases/tag/v5.3.0), official `arm64_linux` archive SHA-256 `2a4afa860ac7aa6968f88df7841823746e5d00ba56affdf9342c2f5254fb776f` (matched against release API metadata). The packed stub entry was `0x4dcdc4`; execution reached the known original entry `0x400580`. All 32 entry bytes matched, execution continued to `main`, and `upx -d` reproduced the original file SHA-256. The packed entry differed from the original, providing a control against treating the unpacking stub as OEP.

This is one known AArch64 fixture. It does not validate unknown-packer OEP discovery, the guide's x86-64 syscall-register procedure, Intel PT, JIT code, or every UPX format.

## Remaining prerequisites

- **bpftrace 0.17.0:** the syscall tracepoint was unavailable from this container's tracefs view; the uprobe attempt failed creating a BPF map with `Operation not permitted`. Entry/exit correlation, attachment behavior, overhead, and lost-record counts remain unmeasured. A separately provisioned Linux environment needs accessible syscall tracepoints/tracefs, working uprobe support, and the BPF/perf capabilities allowed by that kernel's policy. Before measurement, inspect real field names with `bpftrace -lv`; correlate by TID and include syscall exit results. Compare repeated untraced/traced runtimes with a known event count and record consumer-loss diagnostics under both ordinary and stressed buffering. See the [versioned bpftrace reference](https://github.com/bpftrace/bpftrace/blob/v0.17.0/docs/reference_guide.md).
- **Intel PT:** no `intel_pt` PMU exists on this ARM virtual machine. `perf record -e intel_pt//u` failed before capture; even software `task-clock` events were denied. A supported Intel CPU with PT exposed to Linux, permitted perf access, and a decoder using matching executable bytes is required. Check perf's XED build support separately. Capture and inspect AUX loss/PSB synchronization and measure repeated baseline/capture runtimes; no overhead or zero-loss claim follows from the current probe. See [kernel perf access guidance](https://docs.kernel.org/admin-guide/perf-security.html) and [versioned Intel PT documentation](https://github.com/torvalds/linux/blob/v6.12/tools/perf/Documentation/perf-intel-pt.txt).
- **CRIU 3.17.1:** `criu check` failed with missing TUN and namespace/socket operations denied. No dump or restore was performed. A separately provisioned, compatible source/target Linux environment must pass the selected version's feature checks with the resources and privileges required by its chosen workload, before a counter/FD continuity restore test is meaningful. See [CRIU](https://github.com/checkpoint-restore/criu).
- **ECFS/ecfs_exec:** no build, snapshot conversion, or restore was run. Sources were inspected at ECFS `175806336b9c1b815e03e0b8c06f949aa333da51` and ecfs_exec `27e93ae5ce16d1309b4d8f8d5ed7559883b22cec`. ECFS requires live `/proc/PID` context; its [README at that revision](https://github.com/elfmaster/ecfs/blob/175806336b9c1b815e03e0b8c06f949aa333da51/README.md) records snapshot-helper problems and dual 32/64-bit libelf/libdwarf build requirements. The [ecfs_exec README](https://github.com/elfmaster/ecfs_exec/blob/27e93ae5ce16d1309b4d8f8d5ed7559883b22cec/README.md) supplies no usable compatibility matrix. A pinned, supported x86 environment, toolchain, and a specific restorable fixture must be established separately; this ARM run is not evidence that those prototypes restore correctly.

Burneye algorithm history and the Airs article's inaccessible content were not inferred or reintroduced. The x86-64 CRT fragment and Linux execution of the LIEF-transformed artifact also retain their earlier, separately recorded limits.

Raw evidence is delivered outside the repository under the requested audit directory; generated cores and binaries are not part of the website or source distribution.
